1. Pipeline CI/CD

Descrição do Pipeline CI/CD

Automação completa do ciclo de vida da aplicação: da validação unitária à entrega contínua em nuvem.

🛠️ Ferramentas Utilizadas e Papéis
  • GitHub Actions: Orquestrador dos pipelines de CI e CD através de workflows declarativos em YAML.
  • Docker Hub: Container Registry responsável por armazenar, versionar e distribuir as imagens públicas/privadas.
  • Azure Web App: Plataforma gerenciada (PaaS) que executa o container da aplicação na nuvem com escalabilidade.
  • GitHub Secrets: Gerenciamento seguro e criptografado de credenciais do banco (DB_URL, DB_USER, DB_SENHA), token JWT e credenciais de nuvem.
⚡ Continuous Integration (CI) — continuous-integration.yaml

Gatilho (Trigger): Disparo automático em qualquer Pull Request direcionado para a branch main.

Etapas do Workflow:
  1. Git Checkout: Clona o código-fonte da branch usando a action actions/checkout@v4.
  2. Setup Java 21: Provisiona a SDK do Java 21 distribuição Eclipse Temurin via actions/setup-java@v4.
  3. Testes Unitários: Executa mvn test injetando variáveis de ambiente seguras via GitHub Secrets.
Lógica do CI: Atua como um Quality Gate obrigatório. Garante que pull requests com quebras de build ou testes com falha sejam bloqueados antes da integração ao código estável.
🚀 Continuous Deployment (CD) — continuous-deployment.yaml

Gatilho (Trigger): Disparo automático após qualquer Push ou merge aprovado na branch main.

Etapas do Workflow:
  1. Job build-and-push: Realiza checkout, efetua login autenticado no Docker Hub e compila a imagem publicando as tags latest e o hash do commit ${{ github.sha }}.
  2. Job deploy-to-azure: Dependente do término com sucesso do build (needs: build-and-push), atualiza a instância no Azure Web App for Containers com o commit SHA gerado.
Lógica do CD: Garante entregas imediatas, automatizadas e idempotentes. O uso da tag SHA assegura rastreabilidade total entre o código no GitHub e o artefato em execução na Azure.

2. Docker & Containerização

Docker: Arquitetura, Comandos e Imagem

Padronização de ambiente, estratégias de multi-stage build e isolamento da aplicação.

🐳 Conteúdo do Dockerfile
# Etapa 1: Build da aplicação com Maven e Java 21
FROM maven:4.0.0-rc-5-eclipse-temurin-21 AS build
RUN mkdir /opt/app
COPY . /opt/app
WORKDIR /opt/app
RUN mvn clean package -DskipTests
# Etapa 2: Runtime leve com Alpine JRE
FROM eclipse-temurin:21-jre-alpine
RUN mkdir /opt/app
COPY --from=build /opt/app/target/app.jar /opt/app/app.jar
WORKDIR /opt/app
ENV PROFILE=prd
EXPOSE 8080
ENTRYPOINT ["sh", "-c", "java -Dspring.profiles.active=$PROFILE -jar app.jar"]
📐 Arquitetura e Estratégias Adotadas
  • Multi-Stage Build: O processo é dividido em etapa de compilação (com Maven e JDK) e etapa de execução (somente JRE). Código-fonte, dependências de compilação e caches do Maven não poluem a imagem final.
  • Imagem Base Alpine: Uso de eclipse-temurin:21-jre-alpine, reduzindo a imagem de ~800 MB para menos de 190 MB, acelerando downloads no Docker Hub e diminuindo drasticamente a superfície de ataque.
  • Configuração Dinâmica: O parâmetro -Dspring.profiles.active=$PROFILE permite chavear perfis (dev, prd) em runtime sem reconstruir o container.
💻 Comandos Docker Principais
Ação / Objetivo Comando Executado
Build da imagem: docker build -t biooffset .
Execução do container: docker run -p 8080:8080 -e URL=... -e USER=... -e SENHA=... biooffset
Tagueamento: docker tag biooffset usuario/biooffset:latest
Publicação no Registry: docker push usuario/biooffset:latest

5. Desafios & Soluções

Desafios Encontrados e Como Foram Resolvidos

Principais obstáculos de arquitetura, segurança e DevOps enfrentados pelo time e soluções implementadas.

🔐 1. Gestão Segura de Credenciais do Banco Oracle

Desafio: A conexão com o banco Oracle corporativo exige credenciais estritas (URL, usuário e senha) que não podem sob hipótese alguma ser versionadas no repositório GitHub por razões de conformidade e segurança.

Solução Adotada: Parametrização via variáveis de ambiente (${URL}, ${USER}, ${SENHA}) no application-prd.properties. No pipeline de CI e no runtime da Azure, os valores são injetados diretamente via GitHub Secrets e configurações de ambiente de nuvem, mantendo o código-fonte livre de segredos (princípio de Zero Hardcoded Secrets).

📦 2. Tamanho Excessivo da Imagem Docker e Tempo de Deploy

Desafio: Uma imagem Docker contendo o JDK 21 completo e o utilitário Maven gerava pacotes superiores a 800 MB, tornando os uploads/downloads no Docker Hub excessivamente lentos e sobrecarregando a inicialização na Azure.

Solução Adotada: Implementação da estratégia de Multi-Stage Build com runtime minimalista baseado em eclipse-temurin:21-jre-alpine. Apenas o app.jar é transferido para o container final, reduzindo o tamanho em mais de 75% e acelerando o tempo de implantação.

🗄️ 3. Sincronização de Migrações Flyway no Oracle Database

Desafio: Ao instanciar a API em novos containers, o Flyway entrava em conflito com tabelas e objetos previamente existentes no schema Oracle, provocando falha na inicialização do Spring Boot.

Solução Adotada: Adição das configurações spring.flyway.baselineOnMigrate=true e spring.flyway.baseline-version=0 nos properties de produção, permitindo que a aplicação assuma o baseline existente sem travar o deployment.

🏷️ 4. Rastreabilidade de Versões e Idempotência de Deploy

Desafio: A utilização exclusiva da tag latest dificultava a identificação de qual versão de código estava em execução na nuvem e inviabilizava estratégias rápidas de rollback em caso de incidentes.

Solução Adotada: Configuração do pipeline de CD para taguear simultaneamente a imagem com latest e com o SHA do commit (${{ github.sha }}). O deploy na Azure aponta diretamente para a tag do SHA, assegurando rastreabilidade total e auditabilidade.
